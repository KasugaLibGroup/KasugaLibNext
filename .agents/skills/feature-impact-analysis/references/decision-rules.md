# 阶段 1 · 改动分析的规则

## 1.1 能力盘点：三档怎么判

| 「是否存在」列 | 含义 | 阶段 2 的操作类型 |
|---|---|---|
| **直接可用** | 调现有 API 即可 | **消费** |
| **存在需改** | 有，但要加字段 / 加格式 / 改行为 | **扩展/修改** |
| **不存在** | 没有，要造 | **新建** |
| **—**（不需要） | 完全不经过 | 跳过 |

查 `capability-inventory.md` 确定第 3 列，**不许凭印象**。

## 1.2 「用途说明」怎么写

写**这个能力拿来做什么**，用业务语言，一两句话。

| | 例子 |
|---|---|
| ✅ 好 | 拆分/重组时播放动画与音效 → 需要事件系统通知 |
| ✅ 好 | 保存哪两段还连着 → 读档后要能恢复 |
| ❌ 差 | 需要事件系统（只是重复能力名，没说用途） |

**写不出用途却标了「需要」，说明这一行判错了 —— 回头重判。**

## 1.2b 后三项（17/18/19）怎么用

这三项容易混，判错会导致**同一个改动被记两次**。

| 项 | 收什么 | 不收什么 |
|---|---|---|
| **17 音效与粒子** | 播放时机、音量、粒子发射与外观 | 只注册音效资源（那是「5 注册」） |
| **18 领域规则 / 业务逻辑** | 判定条件、状态转换规则、算法 —— 属于业务本身，不属任何基础设施 | 有现成能力可用的逻辑（那就是「消费」） |
| **19 其他新子系统** | 类别上确实是新的，上面 18 项都放不进去（自己给它命名） | 某个已有能力的**实现方式** |

**最容易犯的错**：把「某个能力的新建实现」填进 19。

| 反例 | 正确做法 |
|---|---|
| 需求：给模型加载添加新格式 → 19 填"格式转换器" | 转换器是「4 模型/资产加载」的**新建实现** → 4 标"不存在需新建"或"存在需改"，**19 填"否"** |
| 需求：建网络包系统 → 19 填"包可靠性层" | 它是「2 网络同步」的**新建实现** → 2 标"不存在需新建"，**19 填"否"** |

**判据一句话**：如果这个"新东西"能被归纳到前 18 项里的某一项，
它就属于那一项，**19 只收真正放不进去的**。

> 为什么这么严格：三个真实案例里，最初有 2 个把实现细节写进了兜底项，
> 导致同一改动在盘点表和改动点清单里各记一遍。

## 1.3 归类四问的用途

四个答案决定阶段 2 展开哪些维度：

| 问题 | 答案决定 |
|---|---|
| 玩家能直接感知吗？ | 为是 → 阶段 3 必须有完整的人工实测清单 |
| 用已有能力还是造新能力？ | 造 → 风险重心在「设计是否完整」 |
| 引入新持久化吗？ | 是 → 必须展开 R-PERSIST 全部 6 条 |
| 涉及双端交互吗？ | 是 → 必须展开 R-NET 全部 6 条 |

# 阶段 2 · 风险分析的规则

## 2.1 严重度定义

| 等级 | 含义 |
|---|---|
| **致命** | 数据丢失 / 崩溃 / 不可恢复 / 玩家可利用 |
| **严重** | 功能失效 / 状态错误但可恢复 |
| **一般** | 体验瑕疵 / 需要特定条件才出现 |

> 产出里保留这三行说明即可 —— 读者看到「致命」需要知道是什么意思。

## 2.2 应对方式怎么选

| 应对 | 什么时候选 |
|---|---|
| **改设计** | 风险代价大且加测试也防不住（如「双权威」结构问题） |
| **加测试** | 行为正确即可，测试能覆盖住 |
| **接受** | 影响面极小 / 极端场景 / 修复代价远超收益 → **必须写明理由** |
| **推迟** | 本次不做但要记录 → **必须写清何时处理** |

> 「接受」和「推迟」不是逃避，但**必须留下书面理由**。没有理由的接受，等于默认它不存在。

## 2.3 判定纪律

- **维度不能漏。** 「需要=是」的能力，其下所有维度必须出现在待判定清单里
- **三档判定，不许留空**：`有风险` / `无风险` / `待定`
- **「无风险」必须写具体理由**（「因为 X 所以不会发生」）。**「不适用」不算理由**
- **「待定」必须写什么时候能定**，否则等于没判
- **命中「未建维度」时显式标注**，不许自行发明检查项

# 阶段 3 · 测试策略的规则

## 3.1 层级怎么选

**不是「越便宜越好」。** 层级要和改动性质匹配 —— 选高了浪费，选低了等于没测。

| 改动性质 | 首选层级 | 为什么是这一层 | 还需要人进游戏吗 |
|---|---|---|---|
| 纯逻辑（算法、数据结构、编解码、注册规则） | **纯 JVM** | 秒级、可断言、CI 每次都能跑 | 不用 |
| 渲染输出（像素、着色器、帧缓冲） | **离屏 GL** | 能读回像素做断言（`renderGlTest`） | **要** —— 数字对不代表观感对 |
| 世界内交互（tick、方块、存档加载） | **gameTest** | 真实世界推进、真实存档 | 视情况 |
| 双端与并发 | **多人·专用服务端** | 需要真实网络和两个客户端 | 通常要 |
| **玩家可感知的业务功能** | **手动进游戏** | 只有人能判断「玩起来对不对」 | ——（本身就是人工） |

> **层级名必须写全，不要用 L1–L5 之类的代号。**
> 代号一旦脱离这张表就没人看得懂，而这张表不会跟着产出文件一起发出去。

## 3.2 两条原则（是叠加，不是二选一）

**原则一：偏底层的能力，能用代码测就必须用代码测。**

人能测但不可重复、不可回归、不能每次改动都跑一遍。
把能自动化的东西降级成人工，等于**永久失去这块的回归能力**。

**原则二：偏业务的功能，必须进游戏实测，代码测试替代不了。**

代码测试只能验证「逻辑算得对」，验证不了「玩家操作起来对不对」。
拿列车挂钩举例：

| 这一层能测 | 这一层测不到 |
|---|---|
| 分离条件成立时返回 true | 点挂钩**真的**能分开吗 |
| 坐标重算后的数值正确 | 分开的样子**看起来**对吗 |
| 请求幂等（重复调用返回 false） | 两个玩家同时点，**实际**会发生什么 |

## 3.3 怎么判断该走哪条

| 问自己 | 是 → |
|---|---|
| 玩家能直接感知到吗？ | 必须人工实测 |
| 需要多条件组合或操作序列才触发？ | 必须人工实测 |
| 结果能用数字/布尔描述干净？ | 代码测就够 |
| 结果是「看起来怎样 / 手感如何」？ | 必须人工实测 |

> 某次字体在十个色号下全渲染成黑色。这类问题**开发环境启动一次游戏就能看出来**。
> 但如果清单里没写「进游戏看十种颜色」，就永远没人看。

## 3.4 固定项是哪三项

| 项 | 为什么必须有 |
|---|---|
| **基础可用性** | 没有它，等于假设「功能根本没实现也能过」是安全的 |
| **CI 与代码规范** | 编译、静态检查、现有测试套件 —— 底线 |
| **测试自身有效性** | 一写就过的测试有两种可能：断言太弱，或它测的东西本来就没坏 |

## 3.5 人工实测怎么写

每一项必须写清五件事：

| 列 | 要求 |
|---|---|
| **环境** | 装什么、什么版本、单人还是服务器 |
| **步骤** | 具体操作序列，别人照着能做 |
| **通过标准** | 看到什么算对 |
| **失败特征** | 出问题时看起来是什么样 |

**「失败特征」不能省。** 人不知道正常长什么样，但看到坏的能认出来。
没有它，验收的人只能凭感觉「好像没问题」。

**执行记录也要留**：谁验的、什么日期、什么结果。不记录的话，「测过了」永远是口头承诺。
