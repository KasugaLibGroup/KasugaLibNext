# 示例三：网络包处理系统基础设施

> **设定**：当前 `core/networking` 只有 RPC 会话管理（请求-响应 + 超时），
> **没有序号、重传、分片、背压**。本需求是从零建一层包处理基础设施。
>
> **这是「基建」型需求**，与 [example-01-gameplay.md](example-01-gameplay.md)（玩法）、
> [example-02-extension.md](example-02-extension.md)（能力扩展）相对。
>
> 三类对比最能看出这套流程的用法差异：
>
> | | 玩法 | 能力扩展 | **基建** |
> |---|---|---|---|
> | 玩家可感知 | 直接 | 间接 | **几乎不可感知** |
> | 风险重心 | 状态与同步 | 转换语义 | **契约完整性** |
> | 人工实测 | 最多（10 项） | 多（9 项） | **最少（4 项）** |
> | 可测性 | 中（需进游戏） | 中（需像素） | **最高（假 transport 可模拟一切）** |

# 阶段 1 产物 · 改动分析

## 0. 需求原文

```
添加一个网络包处理系统基础设施，处理客户端和服务端的通信、同步、丢包等问题。
```

**补充澄清**：

- 目标不是替代现有 RPC，而是提供一层"**可靠的包投递**"，让上层不用自己处理丢包。
- 使用者在它之上写业务包（如"开始分离车厢"），不需要关心重传。

## 1. 归类

| 问题 | 答案 | 依据 |
|---|---|---|
| 玩家能直接感知吗？ | **否** | 玩家看不到包，只会间接感受到"操作生效了/没生效" |
| 主要在用已有能力，还是造新能力？ | **造新能力** | 现有只有 RPC 会话 + 超时，无包可靠性层 |
| 引入新的持久化数据吗？ | **否** | 纯运行时状态，不写盘 |
| 涉及服务端与客户端的交互吗？ | **是** | 本需求就是它本身 |

> 归类结论：**基建型**。玩家不可感知意味着人工实测的需求极少；
> 但也意味着**出问题时没人会报 bug**——玩家只会说"卡了""操作没反应"，不会说"包丢了"。
> 这类系统的失效是**静默的**，必须靠自检和日志。

## 2. 能力盘点

| # | 能力项 | 是否需要 | 用途说明 | 项目中是否存在且可直接用 | 最终可能改动的部分 |
|---|---|---|---|---|---|
| 1 | 存档持久化 | 否 | 包状态是运行时的，不写存档 | — | 不涉及 |
| 2 | 网络同步 | **是** | **本需求主体**：定义包的序号、重传、分片、背压 | **不存在需新建** | 新建整个包处理层 |

| 15 | 平台与原生 | 否 | 纯 Java | — | 不涉及 |

| 18 | 领域规则 / 业务逻辑 | 否 | 协议规则属于「2 网络同步」，**不单列** | — | 不涉及 |
| 19 | 其他新子系统 | 否 | — | — | 不涉及 |

**不需要的能力及理由**

- 持久化/资源/模型/渲染/空间/状态机/第三方/脚本/原生：本需求是"把字节可靠地从 A 送到 B"，不碰这些。

**未定项**

- 可靠性等级：**要可靠有序、可靠无序、还是最多一次？** 这决定整个设计，必须在阶段 2 前定。
- 顺带说明：现有 `RpcSessionManager` 的注释里已经暴露过两个历史坑
  （超时溢出、`double-kill` 导致首个 tick 丢弃全部会话），新系统要避开同类问题。

**未展开的两条及理由**

- `R-NET-1` 权威归属：**基建层不决定业务权威**。谁有资格发什么包由使用者定义，
  本层只保证"发了就送到"。判无风险，但要在契约文档里写明"本层不做权限校验"。
- `R-NET-4` 区块外：基建层不关心业务对象在哪里，包的目标是连接而非坐标。判无风险。

## 3. 逐维度判定

| 维度 | 关联改动点 | 判定 | 理由 |
|---|---|---|---|
| R-NET-2 | C1 C4 | **有风险** | 多个玩家同时发包时，序号空间必须按连接隔离；共用全局序号会互相干扰 |

| R-CODEC-1 | C8 | **有风险** | 坏包（长度不符/校验失败）时不能崩，要丢弃并计数 |
| R-CODEC-2 | C8 | **有风险** | 编解码往返必须等价，否则 ACK 与原始包对不上 |

## 5. 应对方式

| 风险 ID | 应对 | 具体做法 | 代价 |
|---|---|---|---|
| K1 | **改设计** | **把契约文档当作交付物**：写明保证什么（有序？可靠？去重？）、不保证什么（不做权限校验、不保证业务语义的原子性）、失败时调用方看到什么。不写这份文档，这个需求不算完成 | 需要作者写清楚，且后续使用者必须读 |

| K3 | **改设计** | 序号按 `(连接 id, 方向)` 二维隔离，不用全局计数器 | — |
| K4 | **改设计** | 发送 API 显式区分 `toClient(conn)` / `toServer()`；服务端侧调用 `toClient` 时抛明确异常 | 调用方要写清方向 |
| K5 | 加测试 | 模拟乱序投递，断言业务处理器按正确顺序被调用 | — |
| K6 | **改设计** | 收到重复序号直接丢弃且不投递给业务层；ACK 照常回 | — |
| K7 | **改设计** | 每次连接建立时重置序号空间；用随机连接前缀避免跨连接撞号 | — |
| K8 | **改设计** | 解包全程包在 try 里；失败则丢弃 + 计数 + 超阈值断开，**绝不让异常冒到 tick 循环** | — |
| K9 | **改设计** | 重传用**指数退避**，且每个 tick 每连接最多重传 N 个包 | 实现稍复杂 |
| K10 | **改设计** | 上限校验**在服务端准入时做**，客户端校验只为提前报错 | — |
| K11 | 加测试 | 三条断开路径各写一个用例，断言清理完成 | — |
| K12 | **改设计** | 心跳包只更新保活时间，不携带业务状态；业务状态走独立的包类型 | — |
| K13 | 加测试 | 模拟一次跑 5 个 tick，断言重传数量被限流 | — |
| K14 | 加测试 | 表驱动：各类包编解码往返断言相等 | — |
| K15 | **改设计** | 配置损坏降级到默认 + warn，不拒绝启动 | — |

**统计**：改设计 10 · 加测试 5

> **基建型的改设计比例最高（10/15 = 67%）**。
> 因为基建的风险几乎全是"设计没考虑到的边界"——
> 契约不清、序号隔离、清理路径、降级策略。这些写错了，测试只能证明错误的行为是一致的。

## 3. 自动化测试方案

> 基建型的**可测性最高**：用一个假 transport 就能模拟丢包、乱序、重连，
> 不需要真实网络。这是它与玩法型最大的差别。

**K2 断开清理**

- 关联：R-LIFE-1 / C5
- 层级：纯 JVM
- 动作：用假 transport 塞入 20 个未确认包 → 触发断开 → 断言未确认队列、分片缓冲、定时器全部为空
- 为什么是这一层：连接状态是纯内存对象，不需要真实网络
- 验收：断开后三处集合 size 均为 0
- 对应的实测项：无（纯逻辑，人不用看）

**K3 序号隔离**

- 关联：R-NET-2 / C1 C4
- 层级：纯 JVM
- 动作：两个假连接同时发同序号包 → 断言互不干扰，各自按自己序号投递
- 为什么是这一层：纯状态机逻辑
- 验收：两条连接各自收到正确顺序的包；无交叉丢弃
- 对应的实测项：M1

**K5 乱序投递**

- 关联：R-NET-3 / C4
- 层级：纯 JVM
- 动作：假 transport 按 [3,1,2,0] 的顺序投递 → 断言业务处理器按 [0,1,2,3] 被调用
- 为什么是这一层：假 transport 可以精确控制投递顺序
- 验收：调用顺序严格为 0→1→2→3
- 对应的实测项：M2

**K6 重传去重**

- 关联：R-NET-3 / C3 C4
- 层级：纯 JVM
- 动作：同一包投递两次 → 断言业务处理器只被调用一次，但 ACK 回了两次
- 为什么是这一层：纯逻辑
- 验收：业务调用次数 = 1；ACK 发送次数 = 2
- 对应的实测项：M2

**K7 重连重置序号**

- 关联：R-NET-5 / C5
- 层级：纯 JVM
- 动作：连接发到序号 10 → 断开 → 重连 → 发第一个包 → 断言服务端接受（不当作重复丢弃）
- 为什么是这一层：连接生命周期可完全在内存模拟
- 验收：重连后的首包被正常投递
- 对应的实测项：M3

**K8 坏包不冒泡**

- 关联：R-CODEC-1 / C8
- 层级：纯 JVM
- 动作：投递长度不符 / 校验失败 / 内容截断的包 → 断言不抛异常、计数 +1、连接保持
- 为什么是这一层：解包是纯数据操作
- 验收：三种坏包都被丢弃，异常被捕获，连接仍可用
- 对应的实测项：无（但 M4 可观察日志）

**K9 重传限流**

- 关联：R-TICK-1 / C10
- 层级：纯 JVM
- 动作：让 100 个包超时，连续跑 1 个 tick → 断言本 tick 实际重传数 ≤ N
- 为什么是这一层：tick 可手动驱动
- 验收：单 tick 重传数不超过配置上限
- 对应的实测项：无

**K13 卡顿追赶**

- 关联：R-TICK-2 / C10
- 层级：纯 JVM
- 动作：一次推进 5 个 tick（模拟卡顿）→ 断言重传数仍被限流，无爆发
- 为什么是这一层：tick 可手动驱动
- 验收：5 个 tick 的总重传数 ≤ 5N
- 对应的实测项：M2

**K14 编解码往返**

- 关联：R-CODEC-2 / C8
- 层级：纯 JVM
- 动作：表驱动——空包 / 最小包 / 满大小包 / 含可选字段的包，编解码往返断言相等
- 为什么是这一层：纯数据操作
- 验收：往返后逐字段相等
- 对应的实测项：无

**K10 服务端准入校验**

- 关联：R-CONFIG-1 / C9
- 层级：纯 JVM
- 动作：构造超过上限的包，绕过客户端校验直接投递给服务端 → 断言被拒绝
- 为什么是这一层：服务端校验点是纯逻辑
- 验收：超限包被拒绝并记录；连接不受影响
- 对应的实测项：M4
